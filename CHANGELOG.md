## [v1.1.0] - 2026-09-02

**The release that turns the family's permission model from "the admin bypasses everything" into record-scoped, fail-closed RBAC, and lets every AI and integration secret move into an encrypted credential vault — inline values stay as the designed fallback until the migration rakes run.** The window is **2026-07-15 → 2026-09-02 (49 days)** and **965 commits across the family**, measured per service from the pointer this repo carried at `v1.0.0` to the frozen head this release bumps to (frontend 347, CRM 335, auth 105, core 78, processor 48, flow 40, bot-runtime 12); the seven `from..to` ranges are listed under *Repository housekeeping* so every count is reproducible with `git rev-list --count`. **Unlike v1.0.0, this release ships database migrations: 22 of them, in three services — auth 9, CRM 5, core-service 8 (`000016`–`000023`) — including four forward-only permission revocations in auth, an irreversible SKU backfill in the CRM, and an irreversible model backfill in core that requires the migrate role to OWN `evo_core_agents`.** Read the upgrade notes before pulling the tag; several of these are one-way doors. `evo-flow-community` and `evo-bot-runtime` ship real deltas this time — no service in the family is an alignment-only re-tag.

Eight themes:

1. **Least-privilege `agent`, and the administrative gates moved server-side.** The default `agent` role is rebuilt as an attendance-only role: auth's data migrations revoke `conversations.read_all` (CRM-181), `conversations.delete` / `contacts.delete` / `pipeline_stages.delete` / `teams.create|update|delete` (CRM-182), `labels.delete` / `macros.delete` / `canned_responses.delete` / `message_templates.delete` (CRM-190) and `macros.create|update` / `message_templates.create|update` (CRM-70) from the existing system role — custom roles untouched, every `down` a deliberate no-op because re-granting would be an escalation relative to a fresh install. The catalog grows 322→333 keys / 49→51 resources: `ai_integration_credentials`, `pipeline_items.update` (CRM-178), standalone `macros.manage` / `message_templates.manage` / `teams.manage` registered in `STANDALONE_ACTIONS_BY_RESOURCE` so the coarse `write` group never confers them (CRM-70), `users.reset_password` (CRM-210), and `custom_attribute_definitions.read` for `agent` (CRM-166). Two grant migrations carry the new keys to installations that already exist, and they cut in opposite directions: `20260815120001` backfills `ai_integration_credentials.*` and `ai_api_keys.*` to `super_admin` and `account_owner` (`agent` deliberately excluded), while `20260818120001` grants the three standalone `.manage` keys to every non-`agent` role already holding the superseded create/update keys — which **widens a create-only role to full manage**, because `.manage` has no finer split. Enforcement followed: auth's `Api::V1::UsersController#check_authorization` runs BEFORE `fetch_user` and layers `users.manage` on `create`/`destroy`/`bulk_create`/`set_password` and any role-set change (EVO-2116/EVO-2026) — that gate previously lived only in the browser; a role update now genuinely replaces instead of accumulating, destroying every non-derived role of the target, so the role reported by `/api/v1/auth/validate` changes for anyone who had collected a second grant (CRM-496); the CRM's `InstallationConfigPolicy#manage?` dropped the `@user&.administrator? ||` term entirely and is now the sole gate of `/api/v1/admin/*`, denying with 403 instead of the 401 that logged the operator out (CRM-366); and the frontend moved `teams`, `macros` and `message_templates` routes from `read` to `manage`, put system roles behind a duplicate-as-custom-role path (EVO-2152), and removed the Macros "Execute" action (CRM-150).

2. **Pipelines become record-scoped, and archived pipelines stop being written to.** `PipelinePolicy::Scope#resolve` returns `Pipeline.accessible_by(user)` instead of `scope.all`, and `update?`, `destroy?`, `archive?`, `set_as_default?`, `dependents?` and the new `update_items?` all compose `accessible_record?` by re-running the same Scope, so a detail action can no longer disagree with the list (EVO-2204); service-token callers stay exempt. EVO-2222 implements the `team` visibility the form already offered (new `pipeline_teams` join table, `has_many :teams`, links dropped when visibility leaves `team`). Card writes moved off the manager-level `pipelines.update` onto `pipeline_items.update`, so an agent can move a card without reshaping the funnel (CRM-178, backfilled by auth migration `20260817120009` to every role that already held `pipelines.update`). EVO-2205 changed two contracts in the same area: `GET /api/v1/pipelines` now returns only ACTIVE pipelines unless the caller opts into inactive ones — every picker built on that endpoint sees a smaller list — and `DELETE /api/v1/pipelines/:id` blocks only on ACTIVE `pipeline_items`, with the refusal text changed from "Cannot delete pipeline with active conversations" to "Cannot delete pipeline with active items" (the error code is unchanged). Four cards close the archived-pipeline hole from both ends: archiving is now informed (`GET /pipelines/:id/dependents`, redacting form names the caller cannot read) and stamps the capture-form slug onto the contact so attribution survives a card delete (EVO-2200/EVO-2207); stage automations and the inactivity scheduler refuse to run on an archived pipeline (EVO-2201); automation rules can no longer push a conversation into one — the guard sits ahead of `execute_pipeline_assignment`, whose `destroy_all` would otherwise wipe every other membership, and the refusal is written to the rule's timeline instead of showing green (EVO-2202); and `pipeline_items` writes on an archived pipeline are rejected outright (EVO-2203). `PipelineStagesController` stopped swallowing malformed writes (CRM-254/CRM-255) and `AutomationRulesController` builds conditions by hand, closing a strong-params bypass that persisted arbitrary jsonb (CRM-298).

3. **AI and integration secrets move into an encrypted vault, with an ordered scope chain (EVO-2250).** Core-service creates `evo_core_integration_credentials` (migration `000019`, Fernet-encrypted with the same `ENCRYPTION_KEY` the registry and processor already share), a `kind` discriminator with a database CHECK that keeps the vault from becoming a token-refresh owner (`static` owns its value; `oauth` carries `value IS NULL` and points at `(owner_store, owner_ref)`, made unique by `000020`), plus `credential_refs` JSONB on `evo_core_custom_tools` and `evo_core_custom_mcp_servers` (`000021`) and `key_hint` / `scope` / `imported_from` / `base_url` on `evo_core_api_keys` (`000016`–`000018`, `000022`). The CRM resolves consumers through `Ai::CredentialResolver`, which returns an `Endpoint` pairing key with `base_url` so a key can never be sent to another provider's URL, and `Ai::ScopeChain` (`BASE_CHAIN %i[installation account]`, walked most-specific-first) exposes `insert_link(scope, before:)` so the enterprise overlay adds an `agency` link without reopening a resolver (EVO-1794). The processor resolves refs by id out of the vault for custom-tool headers, remote MCP headers, official MCP env vars, external agents and the Knowledge Nexus key, with the inline value as fallback. The frontend adds `/settings/ai-credentials` and `/settings/integration-credentials`, and retires the inline secret inputs per consumer off `GET /integration-credentials/migration-state` — a failing guard reads as NOT retired, the safe direction. The umbrella wires `EVO_AI_ENCRYPTION_KEY` onto the CRM web and Sidekiq services on all three deploy surfaces; it must be the same Fernet value core and processor read as `ENCRYPTION_KEY`. Migration is by idempotent, abort-on-drift rake pairs (`ai_credentials:migrate_dry_run|migrate`, `integration_credentials:migrate_dry_run|migrate`), and `Ai::MigrationState.legacy_fallback_active?` keeps the `OPENAI_API_SECRET` path alive until an install has actually moved (CRM-187).

4. **Fail-open closures, in four services (five closures).** Core-service's `EvoAuthService.CheckPermission` granted access on *every* failure, because `httpclient.DoJSON` wrapped transport errors and every non-2xx alike as `NetworkError` and that branch read as "endpoint not implemented" — an outage, a 5xx, a timeout, a 401 or a 403 therefore allowed every `RequirePermission` route; only a 404 now maps to `NotImplementedError`, and even that only with the new opt-in `EVO_AUTH_ALLOW_MISSING_PERMISSION_ENDPOINT=true` (CRM-461). In the same repo's enterprise build, the tenant middleware bound `app.current_tenant_id` to whatever `X-Evo-Tenant-Id` asked for, because `tenant.NewSQLAuthorizer` honours `EVO_LICENSING_PERMISSIVE_MEMBERSHIP` — the new `enforcedAuthorizer` resolves membership first and ignores the flag, reproducing the gem's `TenantPolicy` allow-set, and the plan `agents` limit is now enforced on the real write path (`POST /agents` and `POST /agents/import`, 422 `QUOTA_EXCEEDED`) instead of on a Rails controller the CRM community never defines (CRM-116). Auth's `Api::V1::ResourceActionsController` stopped returning `true` for unmapped actions, `bulk_update_permissions` returns 403 for any `system: true` role instead of answering 200 and being silently reverted by the next `db:seed`, and the new `RbacGrantReconciler` converges `super_admin` with the catalog on every boot (`rails rbac:reconcile_super_admin`, with a read-only `rbac:check_super_admin_drift` that exits non-zero on drift) (EVO-2062/EVO-2152). The processor's `validate_agent_api_key` no longer swallows a `SQLAlchemyError` into `{"valid": False}` — a dead pooled connection is now a retryable 503, not a non-retryable 401 that dropped the customer's message (EVO-2166). And the frontend's `permissionsService` stopped answering `[]` on a failed `/permissions` fetch, which reached the user as a blanket denial: it rethrows, the stale-cache fallback is bounded at one hour past expiry, and `PermissionsContext` gained a tri-state `FetchStatus` with a real load-failure panel (CRM-164/CRM-494/CRM-495).

5. **The AI turn stops failing silently: media forwarded end to end, failures classified, retries bounded.** Media needed both halves of the pair and both shipped: on the CRM side EVO-2179 makes `BotRuntime::DelegationService#build_message_event` emit `attachments: build_attachments` with TTL-signed media URLs, and on the runtime side EVO-2180 buffers those `attachments[]` across the debounce window in `bot_runtime:attach:<contact_id>:<conversation_id>` and forwards them as base64 A2A file parts whose field names match the processor's `extract_files_from_message` — 15 MiB per attachment, 20 MiB per call, mime resolved from `Content-Type` then the CRM-declared type then the extension, with `text/html` and `application/octet-stream` refused so a Rails error page never ships as an image. The buffer's 10-minute TTL is deliberately sized under the 15-minute lifetime the CRM signs those URLs with, so a stale entry never outlives its links. Fetching is gated by `MEDIA_HOST_ALLOWLIST`, read from the process environment only — an allowlist chosen by whoever sends the event constrains nobody — and re-checked on every redirect hop (EVO-2178); `BOT_RUNTIME_SECRET` became mandatory at boot, closing a path where any caller omitting `X-Bot-Runtime-Secret` was authenticated on `/events`. The processor call is retried on network errors and 429/500/502/503/504 with jittered exponential backoff under an overall ceiling (EVO-2167), and a failed turn now sends the customer one sentence through the postback URL instead of going quiet (CRM-236); `AI_CALL_TIMEOUT_SECONDS` went 30→90 in code, in `k8s/configmap.yaml`, and — the part that actually mattered — in every umbrella `.env`/compose file that was pinning it back to 30. On the processor side, provider failures stop collapsing into 500: `provider_errors.py` walks the `__cause__`/`__context__` chain and maps provider-anchored links to 429/-32010, 503/-32011, 502/-32014, 502/-32012 and 413/-32013, with every detail passed through `redact_secrets` and truncated at 600 chars (CRM-236, narrowed by CRM-424); a caller that hangs up now cancels the run and gets 499 instead of burning provider quota for another five minutes; non-audio attachments finally reach the model — the append to `file_parts` had been gated behind `if is_audio`, so an image was stored as an artifact and the agent answered "No content to process" (EVO-2181/EVO-2178); and the pipeline tool was fixed at both ends of the prompt (CRM-235/237/238): stage lines are rendered one per STAGE with a `stage_id` each, the instruction finally tells the model when to act, and the id precedence **inverted** — a `conversation_id`/`contact_id` extracted from the conversation context now WINS over whatever the model passed, a mismatch is logged as `[CRM-237] ignoring …`, and both fields are documented as "DO NOT SET". Google Calendar gained cancel/edit tools and a single-call slot search, at the cost of one behavior change: the per-day business-hours config is now read regardless of the top-level `business_hours['enabled']` flag, so an install that used that flag as a global off switch starts returning slots.

6. **Segments and journeys stop computing the wrong audience.** evo-flow's segment SQL filtered `label_added` / `label_removed` / `contact_deleted` reading `properties`, while the CRM emits `contact.label.added` / `contact.label.removed` / `contact.deleted` with the payload in `traits`: every Label segment computed zero members and a deleted contact kept counting. Both spellings now live in `contact-event-names.ts`, the Label condition matches `traits.labelId` OR `traits.labelName` so definitions saved by the old editor match without a backfill, and the deleted-contacts optimization no longer rewrites the CASE to `WHEN 1=0` on a cold cache (CRM-215). Every `whereProperties` condition now extracts with `JSONExtractString(if(JSONHas(p,'k'), p, traits), 'k')` — the old `properties`-only form made Equals/Contains never match and NotEquals/NotContains always true, a wrong audience rather than an empty one — and the duplicated, drifted operator switches in Performed, LastPerformed, `atomic-processor` and `batch-processor` all collapse into one shared builder (CRM-241). Segment-definition values are now escaped at every interpolation point (CRM-60), and `NotExists` on a custom attribute finally includes contacts that never triggered the change event. On the journey side, `WebhookTrigger` matched any `webhook.` prefix, so every SendGrid/Resend/SES deliverability callback started every journey holding a Webhook trigger — it now requires the exact `webhook.journey_trigger` (CRM-256/CRM-257) — and `JourneyTriggerProcessor` drops events with a blank `contactId` before any contact-scoped work, instead of opening Temporal workflows keyed on the empty string (CRM-271). Template messages deliver again after the EVO-1716 route cutover (CRM-209), CRM 422 refusal reasons reach the run instead of "Bad Request Exception" (EVO-2203) — with two error-string changes that anyone alerting on journey runs must absorb: the 404 text became contextual (`CRM Resource not found (${context.nodeType})`, previously hardcoded `(conversation)`), and a 422's top-level `message` is now overwritten with the CRM's reason, so callers that parsed the old generic text must read `getResponse().error.code` instead. Set Variable finally honors Increase/Decrease — and throws rather than writing a wrong number (EVO-1840). The frontend moved journeys off `apiEvoFlow` onto the CRM's new `/api/v1/journeys*` passthrough proxy (EVO-2191/EVO-2188), leaving campaigns as the only direct evo-flow consumer — which is why `VITE_EVOFLOW_API_URL` stays required in every deployment.

7. **WhatsApp: Baileys removed, connection state made honest, Meta signup in-page.** `Channel::Whatsapp::PROVIDERS` dropped `baileys` and the provider's services, handlers, helper and the `BAILEYS_PROVIDER_USE_INTERNAL_HOST_URL` switch were deleted. Connection truth was reworked around `provider_connection['credentials_verified_at']`, preserved across unrelated snapshots and discarded on close/disconnect, with `record_credential_probe!(:ok|:rejected|:inconclusive)` driving `authorization_error!`/`reauthorized!` (CRM-339) and a new hourly `Channels::Whatsapp::CredentialProbeSchedulerJob` on queue `low` re-asking whatsapp_cloud and notificame whether a token still works (CRM-469; 360dialog excluded because its probe re-registers the webhook). `DELETE /inboxes/:id/hub_connection` discards a Hub connection that never completed, row-locked against a racing `channel.connected` webhook (CRM-368) — the Hub channel is created before Meta's OAuth, so abandoning the flow used to leave an orphan inbox burning plan quota — and the frontend completes the whole connection in-page via `useFacebookSdk` plus `connect_info` / `whatsapp_connect` (CRM-314). A message the provider refuses before sending now ends `failed` with `content_attributes.external_error` instead of showing a checkmark (CRM-448) — which is also a **volume change downstream**: consumers of `message.failed`, EvoFlow automations and alerting included, start receiving events for a class of message that used to be silent. `POST /api/v1/inboxes/:id/set_agent_bot` with a present-but-unknown bot id now answers 404 instead of falling through to the unlink branch with a 200. Browser webm voice notes are transcoded to ogg/opus (CRM-112), Meta's handshake refuses a blank or mismatched `FB_VERIFY_TOKEN` (CRM-286), and `channelStatus.ts` gained a fifth verdict, `unmonitored`, for channel types the backend has no health support for, while `unknown` with a real `health_source` now derives `attention` rather than `active` (CRM-465).

8. **New ingress and catalog work: purchase webhooks, remote product import, and a wholesale model-catalogue refresh.** `POST /api/v1/webhooks/purchases/:provider` turns an approved sale into a contact plus a card on the pipeline's entry stage, with per-platform verifiers for virtu/hotmart/kiwify/cakto, an HMAC-pinned destination in the `d` query param (a platform's body signature cannot cover the query, so a hand-built URL fails closed with 401), a unique partial expression index on `(pipeline_id, purchase provider, purchase_id)` as the idempotency backstop, and a Rack::Attack ceiling because payment platforms burst redeliveries after an outage (CRM-320/CRM-483/CRM-493). `POST /api/v1/products/import_fetch` pulls a Shopify/WooCommerce catalog through SSRF-filtered connectors bounded at 25 page requests / 40s / 15s per request and returns items in the existing bulk-import shape without writing anything (EVO-1785); `Products::ImageIngestor` reports rejected images instead of failing silently (EVO-2226); and blank SKUs are normalized to NULL and backfilled, since the partial unique index had been treating `''` as a real value and rejecting the second product without a SKU (CRM-289). The pinned model list was replaced wholesale in the frontend — the GPT-4/4o/4.1/4.5/3.5 range, Gemini 1.5/2.0 and the 2.5 previews, Claude 3.x, the Together Llama-2 entries, Bedrock `amazon.titan-text-express-v1` and `anthropic.claude-3-*`, Vertex `*-bison`, Perplexity `r1-1776`/`sonar-reasoning` are gone, replaced by a current set with Bedrock ids prefixed `global.` only where Bedrock offers global routing, and four guard specs now hold the line (CRM-424/442/463/482). Core-service narrowed its Gemini listing to current general-purpose chat models by dynamic metadata filter rather than a fixed allowlist, and the agent-repair default moved off `gpt-4.1-nano` — which OpenAI retires on 2026-10-23 and which `sanitizeAgent` was stamping into customer data merely because someone opened the listing — onto the LiteLLM-prefixed `openai/gpt-5.6-luna`, with migration `000023` moving the rows the old repair already wrote (CRM-464/CRM-480, mirrored by the processor's `DEFAULT_REPAIR_MODEL`).

  **auth (9)** — `20260815120001` backfills `ai_integration_credentials.*` and `ai_api_keys.*` to `super_admin` and `account_owner` (additive, idempotent, reversible; `agent` deliberately excluded); `20260817120003` revokes `conversations.read_all` from `agent` (**destructive, forward-only**); `20260817120005` revokes `conversations.delete` / `contacts.delete` / `pipeline_stages.delete` / `teams.create|update|delete` (**destructive, forward-only**); `20260817120007` revokes `labels.delete` / `macros.delete` / `canned_responses.delete` / `message_templates.delete` (**destructive, forward-only**); `20260817120009` grants `pipeline_items.update` to `agent` and to every role already holding `pipelines.update` (additive, reversible); `20260818120001` grants `macros.manage` / `message_templates.manage` / `teams.manage` (additive and reversible, but it **widens privilege** — see below); `20260818120003` revokes `macros.create|update` / `message_templates.create|update` (**destructive, forward-only**); `20260818120005` grants `custom_attribute_definitions.read` to `agent` (additive, reversible); `20260822010001` grants `users.reset_password` to `account_owner` and `super_admin` (routine on `up`, **lossy on `down`**).

  **core-service (8)** — `000016` `key_hint`, `000017` `scope` + CHECK + index, `000018` `imported_from` + partial UNIQUE, `000020` the partial UNIQUE on `(owner_store, owner_ref)` (built on a table created one migration earlier, so empty), `000021` `credential_refs` JSONB on custom tools and MCP servers, `000022` `base_url` — all routine and additive. The two that are not: `000019` creates the vault table, and **rolling it back DROPs that table and destroys every stored integration secret**; `000023` rewrites `evo_core_agents` off the retired model id and is **irreversible AND requires table ownership**.
- ⚠️ **auth `20260817120003` — populate `inbox_members` FIRST.** Revoking `conversations.read_all` from the `agent` role leaves an agent with zero inbox memberships looking at an empty conversation and inbox list, with no auto-recovery, because the CRM's `inbox_members.empty? -> Inbox.all` degrade was removed in the same window. The migration logs the blast radius on `up` (`CRM-181: N agent-role user(s) have ZERO inbox memberships…`) — read that line in the deploy log.
- ⚠️ **Four auth migrations are forward-only.** `20260817120003`, `20260817120005`, `20260817120007` and `20260818120003` all have a deliberate no-op `down`; rolling back the release does not restore the grants, and `db:seed` will not either because the seed no longer lists the keys. Restoring them is an explicit admin action. Separately, `down` on `20260822010001` is lossy — it removes `users.reset_password` from EVERY role, repairable only with `db:seed`.
- ⚠️ **auth `20260818120001` silently WIDENS privilege on existing custom roles.** It grants `macros.manage`, `message_templates.manage` and `teams.manage` to `super_admin`/`account_owner` and to every non-`agent` role already holding the superseded write keys (macros/message templates: `create`/`update`; teams: `create`/`update`/`delete`, deliberately NOT `teams.read`, which lives in `User::BASIC_READ_PERMISSIONS`). Because `.manage` has no finer split, a role that could only CREATE now MANAGES. In a release whose pitch is least privilege, audit your custom roles after this migration runs.
- ⚠️ **CRM `20260826120000` builds a UNIQUE index CONCURRENTLY.** If the database already holds two cards in one pipeline with the same purchase provider + `purchase_id`, the build fails and leaves an INVALID index that an operator must drop by hand before retrying — this one has no self-healing drop. Check for duplicates before upgrading. Both CONCURRENTLY migrations (`20260727120000` and this one) use `disable_ddl_transaction!`: do not wrap the migrate step in an outer transaction.
- ⚠️ **CRM `20260824120000` is irreversible** — a table-wide UPDATE normalizing blank SKUs to NULL on `products` and `product_variants`. Rows whose SKU was genuinely the empty string cannot be recovered from it. Take the usual backup.
- ⚠️ **core `000023` is irreversible AND requires table ownership.** It rewrites `evo_core_agents` rows off the retired `gpt-4.1-nano` onto `openai/gpt-5.6-luna`; because the table is FORCE ROW LEVEL SECURITY it lifts FORCE for its own transaction, so a migrate role that does not own the table fails there — loudly, by design (proven against a staging role that is NOSUPERUSER NOBYPASSRLS). That failure aborts the migrate-core initContainer, stalls every deployment gated on it, and leaves golang-migrate at "Dirty database version 23" until forced. Take `SELECT count(*) FROM evo_core_agents WHERE model = 'gpt-4.1-nano'` first. Rolling back `000019` DROPs the vault table and destroys every stored integration secret — do not roll back after credentials exist.
- ⚠️ **RBAC grants must be in place before the family goes up.** In the auth catalog: `macros.manage`, `message_templates.manage`, `teams.manage`, `pipeline_items.update`, `ai_integration_credentials.{read,create,update,delete}`, `ai_api_keys.*`, `users.reset_password` and `installation_configs.manage`. The two credential resources are **backfilled automatically to `super_admin` and `account_owner` by auth migration `20260815120001`** — only CUSTOM roles need them granted by hand, and `agent` is deliberately excluded. Everything else fails closed — the CRM's macro/template management and kanban card writes 403, core-service answers 403 on the whole vault and on every installation-scope write, and the two new frontend Settings screens are unreachable. `installation_configs.manage` is now the only thing standing between a user and `/api/v1/admin/*`: `administrator?` no longer bypasses it, so an `account_owner` that could reach installation settings before will get 403.
- ⚠️ **Permission checks fail closed in core-service (CRM-461).** Any evo-auth failure — outage, timeout, 5xx, 401, 403, or a 404 without the new opt-in — now denies with 500 instead of granting. Verify evo-auth actually serves the permission endpoint before upgrading; `EVO_AUTH_ALLOW_MISSING_PERMISSION_ENDPOINT=true` covers only the 404 case and is a temporary escape hatch, not a setting. Monitor the permission-check path during and after the upgrade.
- ⚠️ **Enterprise deployments: two new gates in core-service.** Populate `evo_enterprise_tenant_memberships` before upgrading — the new `enforcedAuthorizer` resolves membership before binding `app.current_tenant_id` and ignores `EVO_LICENSING_PERMISSIVE_MEMBERSHIP`, so callers who relied on that flag start taking 403. - ⚠️ **Purchase-webhook enablement checklist (CRM).** Set `PURCHASE_WEBHOOK_SECRET_<PROVIDER>` in `installation_configs` for each platform you enable, `PURCHASE_WEBHOOK_SECRET_DESTINATION` for the public-credential platforms (Hotmart/Kiwify/Cakto), and `FRONTEND_URL`. - ⚠️ **`EVO_AI_ENCRYPTION_KEY` must equal the `ENCRYPTION_KEY` core-service and processor already use.** It is one Fernet key across three services; generating a fresh one for the CRM makes previously stored AI credentials undecryptable. Compose users get it automatically via `${ENCRYPTION_KEY}`; **swarm operators must paste it into two services by hand**, and must likewise fill the blank `MEDIA_HOST_ALLOWLIST=` — the swarm file ships both empty by convention, and deploying it unfilled leaves AI credentials unstorable and media silently undelivered. Neither fails loudly.
- ⚠️ **`AI_CALL_TIMEOUT_SECONDS`: change it in your own `.env`.** The bot-runtime raised its code default 30 → 90 for CRM-236, but every shipped file set `30` explicitly, which overrides the default — the service-side fix was a no-op on every real stack. - ⚠️ **Media forwarding needs BOTH halves — CRM and bot-runtime must move together.** The producer is the CRM's `BotRuntime::DelegationService#build_message_event`, which emits `attachments[]` with TTL-signed URLs (EVO-2179); the consumer is the bot-runtime's buffer-and-forward (EVO-2180). - ⚠️ **evo-flow ↔ CRM message templates break in BOTH directions.** evo-flow at this version calls only the flat `GET /api/v1/message_templates?inbox_id=…` route: against a CRM older than EVO-1716 (nested route only), template-mode send-message nodes 404 and skip the send silently; and a CRM at or after EVO-1716 breaks an evo-flow older than this version the same way. - ⚠️ **core-service ↔ processor, two version couplings.** The MCP wizard's **Test button** on `POST /custom-mcp-servers/test-connection` delegates the real handshake to the processor's own endpoint (EVO-2139) — without a processor at that version the button fails. Do not stage the processor behind core-service on that key.
- ⚠️ **Redaction lists are a three-repo trio with a secret-destroying failure mode.** The frontend's `vaultRetirement.ts::SAFE_HEADER_NAMES`, core-service's Go `secretmerge.safeHeaderNames` and the processor's `_SAFE_HEADER_NAMES` logging allowlist must move together. ## [v1.0.0] - 2026-07-15

**The first stable release of the CRM Community family.** v1.0.0 promotes `v1.0.0-rc7` to GA after a focused stabilization/hardening pass — no new features of size; the window is bug fixes, security hardening, configuration-resolution corrections, multi-tenant/RLS wiring, and a frontend UI-redesign wave. ~135 commits across the family (CRM 43, processor 37, frontend 36, auth 11 net-new, core 8; `evo-bot-runtime` and `evo-flow-community` are alignment-only re-tags with zero delta). **No new database migrations in any service.**

**Family versioning is now unified — the auth "one rc ahead" exception is dropped.** Since rc6 the auth service ran one release-candidate ahead of the family (the rc7 family shipped auth as `v1.0.0-rc8`). For the stable cut that exception is gone: **every family service, auth included, ships as a single `v1.0.0`.** The auth `develop` head that was previously tagged `v1.0.0-rc8` (`2d9884f`) becomes `v1.0.0`; its delta below is measured from `v1.0.0-rc8` (11 net-new commits, a valid non-scrubbed range). `evolution-api`, `evolution-go` and `evo-nexus` keep their own version schemes and are **not** part of the `v1.0.0` tag set — they are pinned by pointer, unchanged since rc7.

Six themes:

1. **Custom Tools & MCP fixed end-to-end (EVO-2125, EVO-2139).** The MCP custom-server **"Test connection"** button — permanently broken because the Go side did a raw `GET /health` that every spec-compliant MCP 404s — is reworked family-wide: core-service now delegates to the processor's new `POST /custom-mcp-servers/test-connection` (mirroring the working `discoverTools` pattern, propagating `X-Evo-Tenant-Id`), the processor performs a **real MCP handshake** instead of a health check, and the frontend guards `tools: null` and shows the fresh discovery count (`tools_count`) instead of the DB-stale `server.tools.length`. **Custom HTTP tools** now bind object payloads (core retyped the `values` field from `map[string]string` to `map[string]interface{}`, fixing the wizard's `__evo_modes_meta__` object 400ing), the processor registers a tool once and rebuilds attached-by-id tools at runtime keeping metadata off the wire, and the frontend adds an attach-to-agent hint plus i18n-key fixes.

Both are strict no-ops with zero behavior change in the community build.

5. **DB/connection resilience under Swarm (EVO-2141, asyncpg/alembic SSL).** The processor's DB pool is hardened against Docker Swarm idle-connection reaping (async engine `pool_pre_ping=True` + `pool_recycle=1800`, libpq TCP keepalives on the sync engine, `max_inactive_connection_lifetime=300` on the raw asyncpg pool), fixing intermittent 500s / "AI not responding". asyncpg now receives the raw libpq DSN (fixing `sslmode` handling for both `require` and `disable`), and the alembic online-migration engine rewrites `sslmode`→`ssl` for **any** value — so Swarm-overlay deployments running `sslmode=disable` stop silently skipping online migrations.

## [v1.0.0-rc5] - 2026-05-27

Hardening release focused on **fresh-install reliability**. The previous rc4 image set, when deployed against an empty Postgres database with all services starting in parallel, hit a race where `evo-ai-processor-community` (Python/SQLAlchemy) created a foreign-key stub `users(id integer)` table before `evo-auth-service-community` (Rails) ran its `InitSchema` migration.
